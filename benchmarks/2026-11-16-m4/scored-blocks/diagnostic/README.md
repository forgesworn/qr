# Scored duplicate blocks: observer only

Pinned Git revision `fabe7f295c6ceffecb96f62d4585a59784838c8c`. The 28-case fixture generator is derived from `benchmarks/2026-11-16-m4/alignment-frontier/run.mjs` at that revision (original SHA-256 `0479ec0449dbd230223fa890f0ca36b3d7a9e05ddaf9df07502d7b4e5fc10efc`). The snapshot and these tools do not depend on previous scratch directories or the fresh 256-case corpus. The builder copies the pinned sources, photo/PNG helpers and seven conformance PNGs from Git; it requires the explicit repository and its installed TypeScript compiler. It writes generated files only to its output directory:

```sh
node /path/to/diagnostic/build.cjs /path/to/qr /tmp/scored-generated
node /path/to/diagnostic/run.mjs /path/to/qr /tmp/scored-generated > /tmp/scored-receipt.jsonl
```

Each case runs the original full decoder and the instrumented full decoder, asserts exact finder lists, complete results and every Work field, and checks the input bytes after each run. The first receipt line records revision, source and tool hashes; each case records frame hash, outcome, Work and counters. The same 28 fixtures include all four thin-centre regressions; some fractional-blur fixtures do not decode at baseline. The first-success cost is given by the complete clean case and additionally by the counters through its first duplicate; a first duplicate is not necessarily a successful decode.

Each scored-list context has insertion-ordered blocks of eight, retaining every original candidate, including scores below 20. The original predicate is evaluated in original point order and its first match is authoritative. The shadow visits blocks and their points in original order, stopping at the first match; every query asserts identical first-match index. For finite nonnegative radius and finite query coordinates, a valid finite block can be skipped if a nearest extremum lies strictly outside the query on either axis and `abs(extremum - query) > radius`. The subtraction order is exactly the original stored-point-minus-query order. Floating subtraction is monotone in the stored coordinate, so a farther coordinate cannot pass the original inclusive square predicate; distance need not be evaluated. Equality remains in the scan. If a block has any nonfinite point or a query coordinate/radius is invalid, the original point predicates are replayed. Bounds are four floating extrema, updated on every later insertion in a block. No other search, scoring, threshold or work-budget decision is changed.

Counters distinguish baseline and shadow x/y/distance checks, block visits/skips/replays and blocks left unvisited after a match, query and insertion validity checks, ordered bound comparisons and distance tests, candidate insertions, four extrema updates per noninitial insertion, block creation, and first-duplicate prefix. A 32-byte estimate covers just four f64 bounds per block. The separate 40-byte illustrative estimate adds an eight-byte flag/alignment allowance; block start/end fields are observer-only because fixed-size group ranges can be derived; layout, capacity, allocation, indexing and traversal costs are not measured. Cumulative creation bytes are summed over contexts and are not peak resident memory; peak estimates are per one context and exclude diagnostic-only bookkeeping. The derived baseline XY total and charged shadow scalar total include the separately reported XY, bound, validity and extrema-update counts; distance checks remain separate. These are rough operation counts, not comparable CPU units, and do not charge every indexing or traversal operation. Observer elapsed time is not a benchmark, and saved comparisons alone are not a performance claim. The TS observer tests the logical equivalent of Rust's duplicate check; it is not a compiled Rust prototype.
